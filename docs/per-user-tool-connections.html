Per-User Tool Connections

Let each seeker connect their own MCP tools through OpenWebUI's native interface, and have the Hubzoid agent run those tools under that person's own credential. No new Hubzoid UI, not one page.

2026-08-16 · rev 1 · source: OWUI docs (native MCP v0.6.31), hubzoid server.py / connections.py / access, this session
Bottom line

Option 2. OpenWebUI owns the connect experience, Hubzoid owns execution. A user clicks + → Integrations → Tools, enables a tool, and completes the OAuth in the browser. OWUI vaults the per-user token. Hubzoid reads that token and runs the tool under the user's identity, on web and, by identity, on Slack. Zero new Hubzoid UI. One open question sizes the whole effort: does OWUI hand the tool token to the backend on each call, or must Hubzoid read and refresh it from OWUI's database.

Status · shipped in 0.7.15, validated live

Built and proven end to end (Linear MCP: user OAuth in OWUI → bridge decrypted the per-user token → agent called it with real data back). Two live findings settled the design: the "open question" above is answered no (OWUI does not forward the tool token, so Hubzoid reads it from the DB), and OWUI only persists the tool-server config when ENABLE_PERSISTENT_CONFIG=True. Both are handled by one operator switch, OWUI_NATIVE_MCP=true, which expands to config persistence plus the tools permissions. Connect step: Admin → Settings → Integrations → External Tool Servers; the server must support Dynamic Client Registration (Linear / Notion / Sentry / Atlassian yes, GitHub no). Step-by-step how-to: docs/mcp.md. Automatic token refresh is implemented (a refresh-token grant written back to oauth_session, matching OWUI's own scheme).

01 The goal, and how it works

Goal: per-user, per-tool OAuth (Odoo, Jira, Zoho and the like), configured and connected entirely in OpenWebUI's own UI, executed by the Hubzoid agent so the hub keeps its skills, sub-agents and restricted/ access. The whole flow rides one identity, so a tool connected once works across surfaces.

03 Database — one DB, dedicated tables

Decision · one database, never two

There are not two databases today. OWUI owns webui.db (SQLite). Hubzoid has no database of its own — it is file-based and reads webui.db read-only for groups and API keys. Keep it that way. Hubzoid's new state goes in dedicated hubzoid_* tables inside the same database, behind one accessor, so a later move to Postgres carries both together with one connection string.

Caution · Hubzoid now writes to the shared DB

Today Hubzoid only reads webui.db. Writing means: use WAL mode to avoid contending with OWUI, keep every table hubzoid_-prefixed so OWUI's own migrator never touches them, and confirm on each upgrade that OWUI's migrations leave unknown tables intact.

05 The one question that sizes the effort

Verify first · does OWUI forward the tool token to the backend

OWUI refreshes and forwards OAuth tokens to downstream services, and Hubzoid is an OpenAI-compatible endpoint. If OWUI forwards the per-tool token to Hubzoid on each call, steps 2 and 4 nearly vanish — Hubzoid reads a fresh Bearer from the request headers. No DB read, no refresh. If it does not (the likely case, since that forwarding is usually the login-session token), Hubzoid does the read-decrypt-and-refresh above. Confirm this before scoping.

08 Risks

Risk · the refresh + schema coupling is the fragile core

Reading OWUI's token table, matching its encryption, and driving refresh from its client registration are all bets on OWUI internals that carry no stability promise. Mitigation: pin the OWUI version, gate every upgrade behind the checklist in section 06, and keep the coupling isolated in one module so a schema change is a one-file fix, not a hunt.

Caution · if the token is not forwarded, refresh is unavoidable

Since Hubzoid uses the token and OWUI does not, OWUI will not refresh it. Hubzoid must, or a connected tool silently dies at token expiry. Do not ship without the refresh path unless section 05 confirms forwarding.
