# Hubzoid 1.1.0

Hubzoid 1.1 has its own web app, the default chat UI. Sign-in, chat,
conversation history and personal MCP connections are part of Hubzoid now, for
one hub or a gateway of many, and `pip install hubzoid` no longer installs Open
WebUI. Open WebUI stays a supported chat UI (Open WebUI mode). In both, every
agent's access is managed in the Console. Code workflows can
now start from authenticated webhooks, failures raise durable alerts, and evals
record multi-turn conversations and tool calls.

Upgrading from 1.0.x? Read [UPGRADING.md](../UPGRADING.md) before you start.
Every change is listed in the [CHANGELOG](../../CHANGELOG.md).

## Highlights

### The web app

- `hubzoid run` opens the web app in your browser: chat at `/`, the Admin
  Console at `/portal/`, one bundle and one sign-in for both.
- Replies stream with their tool steps and reasoning. Stop, edit and resend,
  regenerate with branches, copy, and attach files by picker, drag and drop or
  paste. Code, tables and download links for files the agent makes render in
  place.
- Conversations are stored by Hubzoid: search, rename, archive, delete, and
  read-only share links for signed-in colleagues.
- An account page, a connections page, light and dark themes and a phone
  layout. Branding comes from the hub's `branding/` folder.
- See [quickstart](../quickstart.md) and [branding](../branding.md).

### Sign-in and accounts

- Local mode by default: no sign-in, you are the owner, and the port stays on
  your machine. `HUBZOID_AUTH=true` turns sign-in on.
- Passwords, Google, Microsoft and one standard OpenID Connect provider, with
  Open WebUI's variable names and callback paths, so existing provider setups
  keep working.
- One-time sign-in links for new people and password resets, from the Console
  or `hubzoid admin`. Self sign-up is off by default and needs approval.
- `hubzoid admin create | reset-password | list | set-role` for the server's
  operator.
- See [authentication](../auth.md).

### Access, connections and gateways

- One access model: a person may use an agent only with a grant in the
  Console, whatever the chat UI and however the hub was deployed. The owner is
  provisioned at their first sign-in. `hubzoid doctor` warns about an agent
  nobody may use. See [access management](../access-management.md).
- Administrators add remote MCP servers in each agent's Connectors tab. Each
  person connects their own account, and every chat turn and workflow run uses
  it on every runtime. See [MCP connectors](../mcp.md).
- `hubzoid gateway` serves many hubs behind one web app with no Open WebUI.
  One sign-in covers every agent a person may use. See
  [deployment](../DEPLOYING.md).

### Hosted MCP

- Hosted MCP is OAuth only: an assistant connects after sign-in and consent.
  Open WebUI API keys no longer work there.
- It is on by default for a local run, and `hubzoid run` prints the
  `claude mcp add` line. See [hosted MCP](../mcp-server.md).

### Moving from Open WebUI

- `hubzoid migrate openwebui` moves people (passwords included), external
  sign-in links, conversations and share links. Access is already in the
  Console and stays as it is. Open WebUI is only read. A dry run comes first,
  and re-runs are safe.

### Install and run

- Measured on macOS arm64 with Python 3.12.6 and fresh caches, on a machine
  shared with other work (load average 14 to 21 on 8 cores): a cold `uv`
  install took 53 s for 136 packages (511 MB), a cold `pip` install 202 s for
  137 packages (646 MB). The legacy `hubzoid[openwebui]` took 355 s for 285
  packages (2.1 GB) with `uv`.
- From the installed wheel at load average 12 to 19, the page answered 20 s
  after a first start and about 11 s after later starts.
- `hubzoid init` scaffolds an operations assistant for a fictional shop and
  offers to save a model key when no Claude Code or Codex CLI is signed in.
- The Docker image is slim. `--build-arg WITH_OPENWEBUI=true` builds the
  legacy image. The compose file turns sign-in on.
- `hubzoid doctor` checks the mode, sign-in, the deployment key, an Open WebUI
  install not yet moved and the loopback guard.

### A latest link for reports

`hub.publish_artifact(..., key="board")` tags a publish, and
`/portal/latest/<agent>/<key>` always opens the newest artifact with that key,
for anyone who may open that one. A board a workflow republishes every few
hours keeps one bookmark.

### Webhook workflows

- `@workflow(on_webhook="ticket-created")` starts a code workflow from a named,
  authenticated webhook on the hub's own bridge. Each event is stored once,
  repeats attach to it, and Hubzoid retries a failed event before alerting.
  `hubzoid schedule redrive` retries a failed event explicitly.
- Limits per workflow and per key (`concurrency`, `concurrency_key`), a bounded
  thread pool, and deadlines on runs and on model, agent and Jev calls.
- One engine owns a hub. A bridge waits for, or regains, ownership without
  interrupting chat.
- See [workflows](../workflows.md#named-webhook-workflows-11).

### Alerts and health

- Durable, retried alerts to a webhook, Slack or email for failed and overdue
  runs, failures in a row, failed scheduled evals, a schedule that stopped
  firing and a stale engine. A schedule that keeps failing pauses itself.
- Alerts carry operational metadata and a Console link, never outputs or
  exception text.
- The edge serves `GET /healthz/workflows` for an external uptime monitor.
- See [deadlines and alerts](../workflows.md#deadlines-and-alerts).

### Evals

- Multi-turn cases, tool calls with arguments and results, `expect_tool_args`,
  and `run_as` to run a case as an account.
- A read-only Evals tab on each agent's page. Results of a `run_as` run are
  private to that account.
- See [evals](../evals.md).

## Upgrade requirements

- Read [UPGRADING.md](../UPGRADING.md). Choose to move to the web app or to
  keep Open WebUI (`pip install "hubzoid[openwebui]"` and
  `HUBZOID_UI=openwebui`).
- Run `hubzoid doctor`: every agent needs grants now, and it warns about an
  agent nobody may use. Open WebUI groups and `MCP_ACCESS_GROUP` grant nothing.
- With sign-in on, a deployment that has Open WebUI accounts and no Hubzoid
  accounts does not start until it is moved or set to Open WebUI mode.
- Dry run `hubzoid migrate openwebui`, back up with `hubzoid backup`, stop the
  deployment, then apply with `--apply`.
- Everyone signs in once after the move. Personal connections are connected
  again. MCP clients reconnect with OAuth.
- Back up the deployment key (`secret.key` or `HUBZOID_SECRET_KEY`)
  separately from the data.
- Workflows that use `on_failure`: the POST body is now the alert payload,
  with no `error` field. Repeated failures within an hour arrive as one alert
  with a count. A value that is not an `http(s)://` URL is read as the name of
  an environment variable holding the URL.
- `workflows/settings.yaml` is checked when the bridge starts. A mistake turns
  that hub's workflows off and shows the error in workflow health
  (`hubzoid schedule status`, the Console and `/healthz/workflows`). Chat keeps
  running.

## Not yet verified with real services

These paths are built and tested against stand-ins. They have not been
checked end to end against the real service for this release:

- Google, Microsoft and third-party OpenID Connect sign-in (tested against a
  local OpenID Connect provider)
- Personal connections to third-party MCP servers (tested against Hubzoid's
  own OAuth-protected MCP server)
- A real Claude account connecting to hosted MCP over https
- The Docker images (`docker build` was not run for this release candidate.
  The release pipeline builds and starts both architectures before
  publishing)
- Slack and email alert delivery (tested with injected senders and the email
  preview outbox). No provider-specific webhook signature, such as Zoho Desk's,
  is verified yet. Use the shared-secret header or the timestamped HMAC.

## Known limits

- **Rate limits behind proxies.** Per-address sign-in limits use
  `X-Forwarded-For`. Behind a TLS proxy that sets it, each client is counted on
  its own address. Without one, a client can send its own header and avoid the
  per-address limit. Per-email limits always apply.
- **No stream resume.** A page that reloads during a reply follows it by
  polling, about a second behind, instead of resuming the stream.
- **Providers need registered clients.** A personal connection needs a
  provider that supports dynamic client registration, or a client registered
  in advance with the redirect URI the Console shows. `private_key_jwt` and
  provider-specific authorization parameters (such as Google's
  `access_type=offline`) are not supported. A token without an expiry is not
  re-checked between turns.
- **Microsoft email verification.** A Microsoft email counts as verified only
  when the ID token carries the optional `xms_edov` claim. Without it,
  Microsoft cannot sign in to an existing account by email.
- **Legacy-only sign-in.** GitHub, LDAP, trusted proxy headers and
  claim-based roles and groups are available only in the legacy Open WebUI
  mode.
- **Share links** open for any signed-in person of the deployment. Shares that
  Open WebUI kept private become readable by everyone signed in after the
  move.
- **Deleting a user** removes the account, its sessions, sign-ins, links,
  personal connections and grants, but keeps their conversations and share
  links in this release, although the Console's confirmation says their chats
  are deleted.
- **Turning sign-in on after local mode.** `HUBZOID_ADMIN_EMAIL` and
  `HUBZOID_ADMIN_PASSWORD` give the owner's access only on hubs that have no
  owner yet. A hub that already ran in local mode has the local owner, so use
  `hubzoid admin create <email> --owner` there.
- **Two ways to add a user.** **People → Add user** gives a one-time sign-in
  link. **Add user** on an agent's Access tab still sets a password you share.
- **Proxy logs.** Hubzoid redacts one-time sign-in links and OAuth codes from
  its own access logs. A reverse proxy in front of it logs them unless you
  redact `/api/auth/link/` and the `token`, `code` and `state` query parameters.
- **No API keys for the management API** in the web app mode (Open WebUI keys
  from an old database are ignored). Scripts use a
  signed-in session.
- **Channels.** WhatsApp and Telegram senders are still matched by the hub's
  roster, not by Hubzoid accounts. Slack senders map to Hubzoid accounts with
  `SLACK_IDENTITY_MAPPING=true`.
- **Gateway replies.** In a gateway, the conversation view of a reply running
  on another hub can be about a second behind.
- No per-person limits on uploads or chat, and the web app is in English only.
- **Workflow code that never returns.** A run's deadline cannot stop
  arbitrary synchronous code. It keeps its thread and its ticket's slot until
  it returns, so bound your own network calls.
- **External actions are at-least-once.** A crash or a lost engine owner can
  repeat work done before the last checkpoint. Use `hub.event.key` for
  idempotent writes.
- **PostgreSQL engine restarts.** After a crash, a new engine owner waits up to
  90 seconds for the previous owner's lease. A clean stop does not wait.
- **Alerts start at the upgrade.** The first start looks back 24 hours. Older
  failures are not alerted (no historical backfill). Later downtime of any
  length is caught up.
- **A paused second owner.** With two processes serving one hub on
  PostgreSQL, an old owner paused beyond its lease, whose session ended, can
  claim queued runs as it resumes. They stay pending, without side effects,
  until the owning bridge restarts. Run one bridge per hub.
- **No retention for event and alert records** yet. They stay in the
  operational store, so include it in backups.
