# Hubzoid 1.0.1

Hubzoid 1.0.1 turns a hub into something a team can run: recorded workflows
that act as real people, private artifacts and email, an Admin Console for
accounts and access, and a choice of three runtimes.

Upgrading from 0.9.x? Read [UPGRADING.md](../UPGRADING.md) before you start.
Every change is listed in the [CHANGELOG](../../CHANGELOG.md).

## Highlights

### Workflows

- Markdown tasks (`schedule/*.md`) and new Python code workflows
  (`@workflow`, `@step`) run on one engine, DBOS, with a recorded history of
  every run and its steps.
- Finished steps are saved and not repeated when a run resumes. A step that
  was running when the process stopped runs again, so make steps that change
  other systems safe to repeat. Side effects are at least once, with
  safeguards, not exactly once.
- `hub.call_llm` makes one model call with no tools (text, JSON or a validated
  Pydantic object). `hub.call_agent` runs the full agent. `hub.call_jev` is
  experimental.
- `hubzoid schedule pause`, `resume` and `cancel`. The Console shows runs but
  has no run buttons.
- See [workflows.md](../workflows.md) and [schedule.md](../schedule.md).

### Who a workflow runs as

- Every run acts as an ordinary account: `run_as`, else
  `HUBZOID_WORKFLOW_USER`, else the owner recorded at setup on a
  Console-managed hub. That account's grants decide what the run may do.
- `hub.state`, artifacts, email and personal connections belong to that
  account. `hubzoid schedule list` and the Console's **Runs as** column show
  who each workflow runs as.
- Managers see each run's status, timing and failure summary. In the Console,
  only the account the run acted as sees its result.
- See [workflow-identity.md](../workflow-identity.md).

### Artifacts and email

- `hub.publish_artifact` publishes any generated file as a private artifact
  with a viewer. Share it with people, groups or the hub. HTML runs sandboxed,
  with no network access unless you allow specific origins
  (`HUBZOID_ARTIFACT_ALLOW_ORIGINS`).
- Public links need the **Share artifacts publicly** permission. Publishing
  never grants it.
- `hub.send_email` emails the run's own account over SMTP, or writes to a
  preview outbox. "Accepted" means the SMTP server accepted the message, not
  that it reached an inbox. An ambiguous send is reported, never resent
  automatically.
- See [reports-and-email.md](../reports-and-email.md).

### Admin Console and delegation

- **Add user**, from an agent's Access page or from People, picks an existing
  account or creates a new one and grants its access in one flow. You share
  the sign-in details yourself. Nothing is emailed.
- With Google sign-in and `OAUTH_MERGE_ACCOUNTS_BY_EMAIL=true` configured,
  **Google sign-in only** creates an account with no password.
- Public sign-up stays closed by default. Open WebUI remains the sign-in and
  chat app.
- Delegated managers (Manage access on specific agents) can add people and
  grant only what they hold in those agents. Organization administrators keep
  account actions such as reset, approve and delete.
- Capabilities are grouped, labelled and show whether their settings are
  present. Setting a key never grants access.
- New "Everyone signed in" grants are refused everywhere. Access goes to named
  people.
- See [ADMINISTRATION.md](../ADMINISTRATION.md) and
  [access-management.md](../access-management.md).

### Three runtimes

- OpenAI Agents SDK (API providers through LiteLLM), Claude Agent SDK
  (`claude-local`) and local Codex (`codex-local`).
- The same hub folder, tools, skills and knowledge work with each.
  Controlled tools are hidden from people who may not use them on every
  runtime.
- `claude-local` no longer exposes the box's own Claude account connectors to
  chat users.
- See [providers.md](../providers.md).

### Personal MCP connections

- Each person's own Open WebUI native MCP connections work on all three
  runtimes. On Console-managed hubs each app needs its `connector_<app>`
  capability.
- The optional connection journey (`HUBZOID_CONNECT_JOURNEY`) lets someone ask
  to connect an app from chat or WhatsApp and get a personal link.
- See [mcp.md](../mcp.md).

### Operations

- `hubzoid backup` and `hubzoid restore` cover databases, chat data and hub
  state. See [BACKUP.md](../BACKUP.md).
- `hubzoid doctor --json` gives checks with stable ids for monitoring,
  including `deps.sqlite`.
- The Docker image moves to Debian 13, runs as an unprivileged user and
  publishes only port 3080. Release images are published to GHCR.
- Hubzoid's tables are versioned and upgraded at the first start. A database
  from a newer release is refused.
- In a gateway, the edge tries another bridge for the Console and the agent
  picker's access check when one is down. This is not high availability for
  the gateway.
- Security fixes: the edge no longer shares one visitor's sign-in cookie with
  another, MCP credentials are kept off process command lines, agent child
  processes no longer inherit service secrets, and file tools refuse secrets
  and databases.

## Upgrade requirements

- Read [UPGRADING.md](../UPGRADING.md) and follow its steps in order.
- Back up before the first start, including the gateway's `--data-dir`.
- With a gateway whose bridges run as their own services, restart the bridges
  once after the gateway's first start.
- On Python 3.12, workflows need SQLite 3.42 or newer, or PostgreSQL. Check
  with the Python the hub uses:
  `python -c "import sqlite3; print(sqlite3.sqlite_version)"`.
  `hubzoid doctor` reports it as `deps.sqlite`. Hubzoid supports Python 3.11
  and 3.12.
- Rotate `WEBUI_SECRET_KEY` after upgrading, because of the edge cookie fix.
  Everyone signs in again.
- Database migrations are one way. Going back means restoring the backup.

## Not yet verified with real services

These paths are built and tested without the real service. They have not been
checked end to end against it for this release:

- Google sign-in consent
- WhatsApp delivery
- SMTP delivery over TLS
- AWS Secrets Manager
- Live OpenAI Agents SDK runtime checks

## Known limits

- Removing the public-link permission ends that person's existing public links
  for good. Granting it again does not revive them.
- The Docker path was not re-verified for this release.
- The waiting status may remain on a stopped reply in some cases.
