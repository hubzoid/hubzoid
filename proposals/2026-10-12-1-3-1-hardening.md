# 1.3.1: dependable reports and personal schedules

## Problem

The 12 October review of merged 1.3.0 reproduced incorrect sharing after an
unchanged publish, broken confirmation with required inputs, missing one-off
artifact links, dispatch failures outside failure accounting, stale report
state after stopping, and inaccessible or stale schedule controls. Discovery,
editing saved inputs, and returning to finished work are incomplete journeys.

## Why now

The owner requested these fixes and the key UX improvements on 12 October,
including further issues found in the affected paths. 1.3.0 will not be released.
Ship the combined functionality as 1.3.1 after review and validation.

## What should happen

- Publishing preserves correct access even when bytes are unchanged.
- Confirmed runs use the saved, validated inputs and return all published files.
- Personal schedules record dispatch failures and preserve stopped state.
- People find offered reports, edit their own schedule inputs and timing, and
  find completed work without receiving workflow administration permissions.
- The workspace refreshes active work, gives useful recovery guidance, and
  exposes its controls on phones and to keyboard users.
- A small runnable example shows a useful report, saved correction and repeat use.
- Package metadata, changelog and upgrade instructions identify 1.3.1 as the
  first published 1.3 release. No release is published by this task.

## Scope and non-goals

Use the existing artifact store, workflow identity, DBOS engine, common tool
contract and Ant Design components. No runtime migration, required Hub fields,
new dependency, visual workflow builder, general business-approval system or
provider provisioning. Keep unrelated uncommitted GitZoid work intact.

## Implementation plan

1. Artifact publication and report tools: sharing-aware deduplication,
   confirmation schemas and saved payloads, ordinary artifact results.
2. Personal schedule bookkeeping and series state: dispatch failure accounting,
   recoverable handoff where feasible, stopped-run and key-ownership races.
3. Existing personal APIs/tools and Console: report catalog, input/timing edit,
   owner-bound result lookup, bounded refresh, recovery wording, accessible
   compact controls. Reuse the existing workflow input form.
4. Runnable report example, documentation and version 1.3.1 release record.
5. Re-review the diff and run focused regression checks, one process at a time.

## Open questions

Real company OAuth, SMTP and provider-specific production acceptance remain
release evidence gaps. Record them honestly without provisioning or using
customer systems. Wider roadmap features remain separately scoped.

## Definition of done

Each reproduced defect has a focused regression test. The personal user journey
works in a short synthetic browser check, including phone and keyboard controls.
The example runs without a model for deterministic validation. Changed frontend
code passes lint/build. A final bounded regression selection covers affected
compatibility and identity paths. No full suite runs on this laptop, per the
owner's explicit constraint. Release readiness distinguishes verified fixes
from external validation still required.

### Product and UX conclusion

The bounded report journey is coherent: discover → run with inputs → confirm
where configured → retrieve → schedule → edit/pause/stop → recover → explicitly
save a correction and repeat. It fits the product brief's stabilization priority
and personal usefulness leading to team reuse.

This release does not establish general business-action approval, Mastra/Agno
feature parity, a visual workflow builder, shipped retrieval/memory, or validated
Railway/Maritime hosting. Those remain scoped roadmap outcomes. Chat confirmation
is an accidental-action guard, not proof of human approval. Recent results are
bounded; an exact run reference can retrieve older work. The code and docs are
ready for the remaining release gates, without an unconditional production-ready
claim.
