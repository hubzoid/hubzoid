# Channels: one contract for Slack, GitHub, Linear, email and WhatsApp threads

Status: proposed for 2.0. This is the shared contract. Each provider adapter
builds on it in its own change.

## Problem

People already talk to a hub from Slack, WhatsApp and Telegram, and GitZoid
reads GitHub webhooks. Each surface does it differently, and the gaps show up
as lost or doubled work:

- Today's Slack adapter and the WhatsApp harness acknowledge a message before
  anything is saved. A crash between the acknowledgement and the reply loses
  the request, and the provider will not send it again.
- A provider retry after a slow answer can reach the model twice and post two
  replies.
- People are matched to accounts by email address. Slack shows the email
  only with an extra permission, and in a shared channel every author is
  flattened into one caller.
- Nothing records whether a reply actually reached the thread. When the
  network drops while posting, the next attempt either posts a duplicate or
  gives up silently.
- Every surface keeps its own settings in environment variables. An assistant
  setting up a hub has no file to write and no command to check it.

## Why now

The ready-made hubs start their work in an issue, a mailbox or a chat thread
and must answer in that same place. Durable work items, the operation record
for outside writes, the native chat engine and the secret store now exist, so
a channel can be built from them instead of inventing a fifth copy of each.

## What should happen

**One file per connection.** `channels/<id>.yaml` in the hub folder says which
provider, which agent or workflow answers, who may start work and the
provider's own settings. Credentials are references into the secret store
(`secret:channel/<hub>/<id>/<name>` or `env:NAME`), never values. The same
schema is used by `hubzoid channels validate|apply|export|doctor`, by
`/api/hubs/{hub_id}/channels/...` and by the Console. Applying is
revisioned: an apply against an old revision is refused, never merged.

**Save first, then acknowledge.** A provider delivery is verified against its
raw bytes, normalized and committed in one transaction before the provider
gets its answer. A repeat delivery returns the first receipt. A reused
delivery id with different bytes is quarantined and never runs. Work is routed
after the commit, and anything accepted but not yet routed is picked up again
when the hub restarts.

**One thread, one origin.** Each provider thread (a Slack thread, a GitHub
issue or review thread, a Linear agent session, an email thread, a WhatsApp
chat) is stored with its exact coordinates. Replies only ever go back to those
coordinates. Text in a message cannot choose a different destination.

**Chat threads run in the native chat engine.** A connection that answers with
an agent maps each thread to a native conversation owned by the person who
asked. The engine's queue gives one reply at a time and a bounded backlog, its
idempotency keys absorb repeats, and the conversation is visible in the chat
app. Other people in the same thread get their own conversation and wait their
turn, each under their own access.

**Intake threads start work items.** A connection that answers with a workflow
starts a durable work item keyed by the triggering message, so a retry or a
restart never runs it twice. The workflow posts progress and results with
`hub.thread.post`, which is bound to the item's origin.

**Every reply is a recorded outside write.** Acknowledgements, progress and
results go through the operation record. If the outcome of a post is
unknown, it is marked ambiguous and is never resent on its own. An empty
history listing is never taken as proof that nothing was posted.

**Account links.** Until run identity has its own store, an administrator
links a provider account (provider, workspace and user id) to a hub account
with `hubzoid channels link`. A person with no link, or whose account lost
access, gets one neutral notice and no model call.

**Administration.** A Channels screen in the Console lists connections with
status and revision, recent deliveries with their outcome, threads, replies
that are pending or uncertain, and account links. Every control calls the
same API as the CLI.

## Scope and non-goals

- No new queue, lease or event tables. DBOS, the work item records and the
  chat engine already provide them.
- No provider transport here. Slack, GitHub, Linear, email and WhatsApp are
  separate changes on this contract, with a test adapter for the contract
  itself.
- Typed numbered-question replies and plan approval inside a thread wait for
  the shared approvals and plan review services. Until then, a requester's
  follow-up continues the work as the next turn, and consequential sends wait
  for a person through the work item approval.
- Mirroring progress from one provider thread into another is not included.
- No automatic sending to customers. Customer-visible replies keep their
  write mode (`off`, `draft` or `approve`).

## Open questions

- Run identity, groups and the shared approvals service are separate work.
  The account link table and the approval adapter here have the shape those
  services will take over.

## Definition of done

- One verified delivery starts one piece of work, across duplicate deliveries,
  two workers and a restart between commit and reply.
- A reply always lands in its origin thread, once, or is shown as uncertain.
- An unlinked or unauthorized sender never reaches a model.
- A connection set up by file, by CLI, by API or in the Console has the same
  revision and the same effective settings.
- Focused tests on SQLite, and the same store tests on PostgreSQL in CI.
